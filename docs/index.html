O que é

problema → padrão portátil

O sdd-kit transforma o Spec-Driven Development num conjunto de skills que o Claude Code carrega automaticamente em toda sessão. Em vez de reexplicar o processo a cada projeto, você invoca a skill certa e ela gera o artefato certo, no lugar certo.

A ideia central é auditoria persistida: o repositório mostra todo o caminho feito — princípios, requisitos, design, tasks, veredito — sem depender do histórico da conversa. Qualquer pessoa, agente ou ferramenta consegue auditar depois, lendo arquivos versionados.

Tudo vive num plugin do Claude Code: as skills (skills/sdd-*), os assets (sdd/ — templates e guidelines que as skills reaproveitam via ${CLAUDE_PLUGIN_ROOT}) e o hook de trava. Instala com /plugin, sem copiar nada à mão.

Sobre o SDD

conceito · origem · diferencial

O que é

Spec-Driven Development inverte quem manda no processo. No modelo tradicional, o código é a fonte da verdade e a documentação corre atrás. No SDD, a especificação é a fonte da verdade e o código é um artefato derivado dela. Você não pede código direto: descreve com precisão o quê e por quê — de forma verificável — e o agente deriva o como. A spec é viva, versionada, e cada critério de aceite vira prova (teste/evidência).

De onde veio

A ideia de "a especificação guia a construção" é antiga — vem da engenharia de requisitos e de práticas como Design by Contract (Bertrand Meyer), TDD (Kent Beck), BDD (Dan North), DDD (Eric Evans) e os ADRs/RFCs. O que mudou foi a era dos agentes de IA (2024–2025): com LLMs escrevendo código rápido, o gargalo deixou de ser digitar e passou a ser especificar intenção sem ambiguidade. Aí o SDD virou prática nomeada, com a tese de que a spec é o artefato durável — o código é regenerável.

Os famosos

GitHub Spec KitCLI specify; constitution → specify → clarify → plan → tasks → analyze → implement. Agnóstico de agente.
Amazon KiroIDE agêntico da AWS: requirements (EARS) → design → tasks, com steering files e hooks.
TesslAbordagem spec-centric: a spec como artefato central, com registro/versionamento.

Por que usar

  • Erra no barato (texto) antes de gastar no caro (execução/código).
  • Tira a ambiguidade — a IA para de adivinhar escopo e alucinar features.
  • Output revisável: produto e engenharia revisam intenção antes de qualquer linha.
  • Trilha auditável no repo, independente do histórico da conversa.
  • Rastreabilidade ponta a ponta: requisito → critério → task → evidência.

Quando usar

use

Feature nova, mudança de comportamento/contrato/API, trabalho com mais de uma pessoa, contexto que exige auditoria, e sempre que a IA for implementar algo não-trivial.

evite

Spike/protótipo descartável, correção de uma linha óbvia, exploração pura. SDD é peso proporcional — para o trivial, ele atrapalha.

Nosso diferencial · por que este kit existe

Spec Kit e Kiro são ótimos, mas genéricos. Este kit pega a maturidade da comunidade e soma auditoria persistida + governança de entrega + disciplina de evidência, num pacote que instala em um comando e roda em qualquer repositório:

  • Nativo no Claude Code, em qualquer projeto — skills globais, disparo por linguagem natural, nada copiado por repo.
  • Veredito de saída auditável (acceptance.md) contra o diff da branch — o que Spec Kit/Kiro não têm.
  • Constitution como lei do projeto — princípios inegociáveis que gateiam todas as fases.
  • Gate de consistência (sdd-analyze) antes de gastar execução.
  • Disciplina de evidência — nenhuma task fecha sem prova objetiva colada.
  • EARS + Gherkin: requisito sem ambiguidade e critério verificável, juntos.

delivery repete uma task por turno até fechar o backlog

O sdd-discovery é opcional e roda uma vez por projeto. O coração é linear: requirements → aprovação → design → backlog → delivery → acceptance. O sdd-delivery repete, uma task por turno, até fechar o backlog; então o sdd-acceptance emite o veredito.

O gate é a regra de ouro. A sdd-requirements sempre para e pede um "aprovado" humano explícito. Ela nunca gera plano nem código no mesmo turno — é o ponto onde produto decide antes de engenharia executar.

As 9 skills

o que cada uma faz e o que produz

01sdd-constitution
princípios · opcional · 1x

Define os princípios inegociáveis do projeto — padrões de código/teste, política de erro e segurança, camadas proibidas, processo. É prescritivo e governa todas as fases.

→ CONSTITUTION.md na raiz (1 por projeto, versionado)
02sdd-discovery
baseline · opcional

Explora o projeto real (pastas, deps, integrações, camadas) e cria/atualiza um retrato técnico atual — não aspiracional. É descritivo, complementa a constitution.

→ ARCHITECTURE.md na raiz (1 por projeto, documento vivo)
03sdd-requirements
especificar · gatilho de entrada

Transforma história, descrição, ticket ou código em requisitos: problema, escopo dentro/fora, requisitos em EARS, critérios de aceite (Dado/Quando/Então), premissas. Faz o clarify e cria a pasta numerada da feature.

→ specs/<NNN>-<slug>/requirements.md · status awaiting_approval
✋Aprovação humana
gate obrigatório

Não é uma skill — é a parada. Os requisitos são resumidos e submetidos a você. Só um "aprovado"/"segue" explícito libera o próximo passo. Sem branch, sem código antes disso.

requirements.md → approved
04sdd-design
planejar · pós-aprovação

Converte os requisitos aprovados em estratégia técnica: impacto por arquivo, dependências, riscos, ordem de execução e como cada critério será provado. Recusa rodar sem aprovação e respeita a constitution.

→ design.md · cita as guidelines aplicáveis
05sdd-backlog
decompor

Quebra o design em tasks executáveis e verificáveis. Cada task carrega origem (rastreio ao requisito), evidência esperada, bloqueios, status e marcador [P] de paralelismo.

→ tasks.md · nada órfão, tudo rastreia a um critério
06sdd-analyze
consistência · gate

Checa coerência entre requirements ↔ design ↔ tasks antes de gastar execução: tudo coberto, nada órfão, nada fora do escopo, nada contra a constitution. Não escreve código.

→ veredito consistente / inconsistente (bloqueia se vermelho)
07sdd-delivery
executar · 1 task/turno

Implementa a partir dos artefatos reais, aplicando as guidelines (TDD primeiro). Só marca uma task como done com evidência objetiva colada — teste verde, saída, diff.

→ código na branch + evidência em cada task
08sdd-acceptance
validar · veredito

Confere a entrega contra o diff da branch: escopo bate com os requisitos? cobertura contra o piso da constitution? caminhos de erro e NFR provados? Emite o veredito auditável.

→ acceptance.md · aprovado / com-ressalvas / reprovado
✳sdd-state
transversal · trava & retomada

Mantém o STATE.md (o que está rodando, onde paramos) e o .sdd/lock: uma feature ativa por vez. O hook sdd-lock bloqueia escrita fora da branch dona — duas janelas não se sobrescrevem.

→ STATE.md + .sdd/lock · lock advisory reforçada

Artefatos & auditoria

a trilha que fica no repositório

Cada feature vive numa pasta numerada dentro de specs/ do projeto-alvo. O número <NNN> é o próximo livre; o <slug> é o título em kebab-case. A CONSTITUTION.md e o ARCHITECTURE.md ficam na raiz, únicos por projeto.

<projeto>/ ├── CONSTITUTION.md # princípios inegociáveis (sdd-constitution) ├── ARCHITECTURE.md # visão técnica real (sdd-discovery) ├── STATE.md # o que roda + histórico (sdd-state) ├── .sdd/lock # trava, reforçada pelo hook sdd-lock └── specs/ └── 001-exportar-relatorio/ ├── requirements.md # o quê e por quê + critérios ├── design.md # estratégia técnica + estratégia de testes ├── tasks.md # tarefas + casos de borda + evidência └── acceptance.md # veredito final da entrega

Cada arquivo tem um cabeçalho Status:. O estado do trabalho vive no arquivo, não na conversa — é isso que torna a auditoria independente do chat.

Instalar no Claude

plugin do Claude Code · uma vez por máquina

O sdd-kit é um plugin + marketplace do Claude Code. Instale de dentro do Claude Code, sem mexer em ~/.claude na mão:

# de dentro do Claude Code
/plugin marketplace add duviolin/sdd-kit
/plugin install sdd-kit@sdd-kit

As skills ficam disponíveis como /sdd-kit:sdd-requirements (e disparam também por linguagem natural); a trava sdd-lock é ativada pelo próprio plugin. Update e uninstall são gerenciados pelo /plugin.

Para testar localmente sem instalar, a partir do clone do repo:

claude --plugin-dir .
# validar o pacote antes de publicar:
claude plugin validate .
Abra uma sessão nova. O plugin é carregado no boot da sessão — as skills só aparecem numa sessão iniciada depois da instalação.

Como rodar

o ciclo de uma feature

Dentro de qualquer projeto, numa sessão nova do Claude Code:

  1. Descreva a feature — ou invoque /sdd-kit:sdd-requirements. Ela cria specs/001-<slug>/requirements.md e para pedindo aprovação.
  2. Revise os requisitos. Responda aprovado (ou peça ajustes). Só então o fluxo avança.
  3. /sdd-kit:sdd-design gera o design.md; /sdd-kit:sdd-backlog gera o tasks.md.
  4. /sdd-kit:sdd-analyze confere a consistência entre requirements, design e tasks antes de codar — bloqueia se algo não bate.
  5. /sdd-kit:sdd-delivery executa uma task por turno, com teste e evidência. Repita até fechar o backlog.
  6. /sdd-kit:sdd-acceptance confere contra o diff da branch — cobertura contra o piso da constitution, caminhos de erro e NFR provados — e escreve o acceptance.md com o veredito.

Trava & retomada: ao começar, o /sdd-kit:sdd-state registra a feature ativa no STATE.md e crava o .sdd/lock. O hook sdd-lock impede outra janela de escrever fora da branch dona; quando voltar, "onde paramos?" lê o STATE.md e retoma no ponto.

As skills também disparam sozinhas por linguagem natural — dizer "quero uma feature de X" tende a acionar a sdd-requirements; "implementa" ou "segue" aciona a sdd-delivery. Invocar por /nome é só a forma explícita.

Exemplo real

do pedido cru ao merge · resumido

Um pedido de produto de uma linha vira uma entrega auditável, sem pular etapas nem gastar execução em cima de um pedido ainda ambíguo.

Você: "preciso de um campo novo no perfil do usuário para cadastrar um segundo telefone"
  1. A sdd-requirements dispara (o "preciso de…" já aciona). Ela lê a CONSTITUTION.md e a ARCHITECTURE.md, descobre onde vive o perfil e como telefones são validados hoje.
  2. Clarify — ela te devolve perguntas antes de escrever nada: é opcional? tem tipo (celular/fixo)? qual principal? valida DDD/país? aceita duplicado? impacta SMS/notificação? LGPD? Você responde.
  3. Ela grava specs/001-segundo-telefone/requirements.md com Status: awaiting_approval: 
    # escopo
dentro: campo "telefone secundário" opcional no perfil
fora:   verificação por SMS · telefone como login

# requisitos (EARS)
R1  WHEN o usuário salva com telefone secundário válido,
    THE SYSTEM SHALL persistir no formato E.164.
R2  IF o secundário for igual ao primário,
    THEN THE SYSTEM SHALL rejeitar com mensagem clara.
RN1 THE SYSTEM SHALL tratar o número como dado pessoal (LGPD).

# critérios de aceite
CA1 Dado um perfil sem 2º telefone, quando informo um número
    válido e salvo, então ele aparece salvo.
CA2 Dado um número inválido, quando salvo, então vejo erro
    e nada é gravado.
  4. GATE. Ela para e resume, pedindo aprovação. Nada de design, branch ou código ainda. aprovado → esta é a sua "história aprovada".
  5. sdd-design vira design.md (onde tocar, riscos, como provar cada CA) → sdd-backlog quebra em tasks.md (com [P] onde dá pra paralelizar).
  6. sdd-analyze confere: todo CA tem task? nada fora do escopo? nada contra a constitution? Consistente → libera.
  7. sdd-delivery faz uma task por turno com TDD e cola a evidência (teste verde). Repete até fechar o backlog.
  8. sdd-acceptance confere o diff da branch contra os requisitos e escreve acceptance.md → veredito aprovado, pronto pra merge.

No fim, o repositório carrega a trilha inteira — do pedido de uma linha ao veredito — sem depender do histórico da conversa:

specs/001-segundo-telefone/ ├── requirements.md # approved ├── design.md # done ├── tasks.md # todas done + evidência └── acceptance.md # veredito: aprovado
